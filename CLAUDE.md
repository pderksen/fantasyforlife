# Fantasy For Life

## Project Overview
Fantasy football roster viewer for a long-running league. Pulls roster data from the Sleeper API and generates HTML tables showing all rostered players organized by owner.

- `docs/photos.md` — photo pipeline: the gitignored inbox, target dimensions per slot, format and naming, the optimize command

Commit messages cite its item numbers ("Close #14"), so it stays reachable by name. Read it for reasoning behind decisions, especially declined ones, never as a description of current state: a closed item can be reverted afterward without the item being updated. ## Key Concepts

**Roster Snapshots**: Three point-in-time JSON captures per season in `data/<season>/`:
- `rosters-pre-draft.json` — full carryover roster with keepers flagged, captured before the draft
- `rosters-post-draft.json` — generated from draft picks (can be created retroactively)
- `rosters-end-of-season.json` — after NFL Week 18
- Each snapshot is self-contained with resolved player names, positions, NFL teams. NFL seasons span calendar years (e.g., 2025 = Sep 2025 – Feb 2026). Shape: `src/types.ts`, also reproduced in `docs/data-capture.md`.

**Pre-Draft Snapshots**: The **entire** carryover roster (`roster.players` — Sleeper holds last season's roster in the new league until the draft runs), with players listed in `roster.keepers` marked `keeper: true`. Kept players appear in *both* arrays, so `keepers` is the only thing distinguishing them; it is `null` until the owner picks, max 3 per `settings.max_keepers`. Owners choose on their own schedule, sometimes right up to draft day, so `takeSnapshot()` names the teams still missing and the command is safe to re-run — each run overwrites the capture.

**Post-Draft Snapshots**: The roster a team left the draft with (its keepers, then its picks), always exactly `LEAGUE_FACTS.rosterLimit` players. Rosters ordered by draft slot; keepers first (sorted by position), then picks in draft pick order.

**Sleeper does not put kept players on the draft board.** A keeper year's board carries the picks alone and `is_keeper` is `null` on every one of them (verified against the 2026 draft: none of the 30 kept players appears). So `takePostDraftSnapshot()` reads keepers off the live `/rosters` response and resolves them through `/players/nfl`, which is the only reason that fetch happens here at all. A throwback year keeps nobody, so `keepersByRoster` is empty and the fetch is skipped.

**The board is not trimmed to the roster limit either, and the survivors are read off the live roster.** 2026's board ran a full 17 rounds against 14 open slots, so every team over-drafted and cut back afterwards, and which picks a team cut was its own call: one kept a round-15 pick over a round-13 one, so "first N in pick order" would have named the wrong player. That makes this a **point-in-time capture: run it once the draft ends and before waivers open.** A roster that has since moved on falls back to the first N picks in draft order and is named in a warning; the fallback is also what a retroactive rebuild of an old season gets.

**A cut closes a hole in the round numbers; a trade leaves one.** Both look the same in a team’s kept picks and only one is real. A traded-away round has **no pick on the board at all**, so its gap is a fact about the draft and stays. A cut round **does** have a pick, so its gap is an artifact of the oversized board, and every later pick shifts up one to close it. Sanger cut a round-13 pick in 2026, and without this their last two picks read 14 and 15 while their trades correctly left them a doubled round 6 and no round 7. The shift runs on the live-roster path only: the fallback cannot tell a cut from a stale roster, so it leaves the board’s own numbers alone. **Rounds are stored but never printed** (see Roster & Player Ordering), so this shift is invisible on the page and still load-bearing: it decides which tier a pick buckets into, here and again on the next season’s pre-draft page.

**Keepers are stamped with a `keeperTier`.** They were not drafted this season, so no round places them, and the rules settle it instead: a kept player climbs one tier from wherever the previous season’s draft put him. `loadKeeperTiers()` works that out at capture and the value lands in the snapshot, which is what lets a page regenerate from its own file with no other season on disk. A keeper it cannot place is named in a warning and renders in the top tier.

**Draft Data**: Immutable. Saved as `draft-picks.json` and `draft-traded-picks.json` — no date suffix needed. Both are written by `--snapshot-draft` on the first run that finds them missing, via `saveDraftPicks()` / `saveDraftTradedPicks()` in `snapshot.ts`, which **never overwrite an existing file** — the copy on disk is the record. `draft-traded-picks.json` is stored as the raw response text, not re-serialized JSON: Sleeper returns its `draft_id` as a bare integer past 2^53, so a parse/stringify round trip silently rounds it off.

**Player Data**: Sleeper `/players/nfl` (~15MB as of Aug 2026; their docs still say 5MB) fetched during `--snapshot` runs, used in-memory to resolve player IDs — not saved to disk. Fetched during `--snapshot-draft` **only when a roster reports keepers**, since draft picks carry their own metadata and keeper ids carry none; a throwback year skips it.

**Traded Picks**: Fetched from `/league/{id}/traded_picks` and saved **unfiltered** (every pick, every draft season) with both resolved and raw data. Re-fetched with each snapshot command until the season seals. Pages narrow the list at render time. See Traded Picks section below.

**Trade Log**: Every completed trade in a season's league, resolved to owner and player names and dated, saved as `data/<season>/trades.json`. **Archive only, no page.** Built by sweeping `/league/{id}/transactions/{week}` for weeks 1–18 of that **one** league (not the lineage — a season's log is what happened that season). Captured by every `--snapshot` run and by `--trades`; seals like traded picks. A season with no trades gets no file. Why there's no page, why players carry no NFL team, and the JSON shape: `docs/data-capture.md`.

**HTML Output**: `output/<season>/` (one per snapshot type) + `output/index.html` home page. Roster pages include chip-style nav bar. Every roster page and the home page show a "Traded Picks" section. Table cells color-coded by position. Footer shows capture timestamp in Pacific time.

**Excel Output**: every roster page has a `rosters-<type>-<season>-ffl.xlsx` twin beside it, written by the same run through `writeRosterOutputs()` in `index.ts` — the page links its own workbook, so one is never written without the other. Two sheets: the roster grid with its formatting intact, and that page's traded picks. Nothing reads these back. See the Excel Export section.

## Sleeper API
- Docs: https://docs.sleeper.com/ — Base URL: `https://api.sleeper.app/v1` — No auth required
- Key endpoints: `/league/{id}`, `/league/{id}/rosters`, `/league/{id}/users`, `/league/{id}/drafts`, `/draft/{draft_id}/picks`, `/league/{id}/traded_picks`, `/league/{id}/transactions/{week}`, `/players/nfl`
- `/league/{id}/traded_picks`: `roster_id` = original owner, `owner_id` = current owner (both numeric despite the name). Carries **no date** — trade dates come from transactions.
- `/league/{id}/transactions/{week}`: one week per call, no all-weeks endpoint. Both callers go through `sweepTrades()`, which keeps `type: "trade"` + `status: "complete"`. `getPickTrades()` sweeps the **whole league lineage** (`getLeagueLineage()` walks `previous_league_id`) and then keeps only trades with a non-empty `draft_picks` array, because next year's picks are traded in this year's league. `getTrades()` sweeps **one league** for the trade log. `status_updated` = accepted, `created` = proposed.
- Preseason and offseason trades are filed under `leg: 1`, so the weeks 1–18 sweep does catch August activity (verified 2026-08-05 against a live pre-draft trade). `league.settings.leg` also reads `1` while status is `pre_draft`.
- A trade names what each roster *gained*: `adds` maps player_id → receiving roster, `draft_picks[].owner_id` is the receiving roster, `waiver_budget` moves FAAB. `drops` is the mirror image of `adds` and carries nothing extra.
- `users[].is_owner` is `null` for non-commissioners, not `false` (verified 2026-08-04 against the 2025 league: 9 of 10 users `null`).
- Rate limit: 1000 calls/min
- **Consumed picks persist**: a completed league still returns its own season's traded picks, so pre-draft pick state stays recoverable after the draft
- `roster_id` → `owner_id` is stable across the season rollover (verified 2025→2026), so raw pick data isn't ambiguous between leagues
- `/players/nfl?position=X` filters, but repeated `position` params are **last-wins, not OR** — multi-position needs one call per position, so the single 15MB fetch (~0.5s) is usually better

## Commands
- **npm 12 swallows the first `--`.** Every `npm run dev -- --flag` below needs a *second* one (`npm run dev -- -- --generate 2026`) or it dies with `EUNKNOWNCONFIG: Unknown cli flag`, and `npm run dev -- --help` prints npm's own help instead of the CLI's. Verified on npm 12.0.2. `node dist/index.js --generate 2026` takes flags cleanly and skips the rebuild.
- `npm run build` — compile TypeScript
- `npm start` — run `dist/index.js` without recompiling. Same `--` caveat. `.github/workflows/refresh.yml` calls `node dist/index.js` directly at every step, not npm.
- `npm run dev` — regenerate `output/index.html` and open it in the OS default browser (local preview; no server, pages load over `file://`)
- `npm run dev -- --help` — usage
- `npm run dev -- --snapshot <pre-draft|post-draft|end-of-season> [league_id] [--force]`
- `npm run dev -- --snapshot-draft <season> [league_id]` — post-draft from draft-picks.json; works retroactively
- `npm run dev -- --generate <season> [type]` — regenerate HTML (omit type for all)
- `npm run dev -- --traded-picks [league_id]` — fetch traded picks standalone
- `npm run dev -- --trades [league_id]` — fetch that league's trades to `data/<season>/trades.json`. Generates no page. Takes a **league id, not a season**: trades live in the league that recorded them, so backfilling an old year means naming that year's league.
- All commands rewrite all six root pages: `output/index.html`, `output/tiers.html`, `output/history.html`, `output/prizes.html`, `output/rules.html`, `output/gallery.html`. The frozen `output/rules-<season>.html` copies are static committed files and no command writes one.

## League
Sleeper mints a **new league ID every season**; `previous_league_id` chains them backward.
`DEFAULT_LEAGUE_ID` in `src/index.ts` is per-season and must be updated each year.

| Season | League ID | Draft ID |
|--------|-----------|----------|
| 2025 | `1220634180434526208` | `1220634181302767616` |
| 2026 | `1331127568820109312` | `1331127568832667648` (Aug 29, 2026) |

- Find next season's league: `/user/{user_id}/leagues/nfl/{season}` — grab any `user_id` from the current league's `/users`
- Find drafts: `/league/{id}/drafts`
- `draft.draft_order` maps `user_id` → slot; use it to verify `DRAFT_ORDERS` in `tiers.ts`

## Team Names

**`South Town FF` is written `South Town Freedom Fighters` everywhere it fits.** Sleeper carries the abbreviation; the league's own name is the full one, so it is corrected on the way in like `ClovisJets` → `Clovis Jets`. The short form survives only as the *key* in `OWNER_NAME_OVERRIDES` — that key is Sleeper's string and must stay verbatim or the correction stops firing.

Abbreviating is fine where a full slate of names would not fit and the reader already has the context. The League History table and the Prize Tracker both do it **at render**, so the data keeps the full names every join key uses. History abbreviates via `shortenForHistory()` in `html.ts`, so `LEAGUE_HISTORY` still stores full names: a tie drops both teams to city words via `TEAM_CITIES`, and "South Town Freedom Fighters" renders "South Town FF" there and only there. Full names are the default everywhere a team is identified on its own — roster column headers, the draft order card, honor cards, traded-pick owners.

**Renaming a team is a source *and* data edit.** `applyOwnerNameOverride()` runs at capture, so the corrected string is what lands in the snapshot JSON, and every join key downstream matches on it: `DRAFT_ORDERS` in `tiers.ts`, the roster grid's column ordering, `SEASON_HONORS`. Sealed seasons never re-fetch, so nothing will ever rewrite their files for you. The full sweep:
1. `OWNER_NAME_OVERRIDES` in `snapshot.ts` (add, keeping Sleeper's string as the key)
2. `DRAFT_ORDERS` in `tiers.ts`, and any hand-written name in `league-info.ts`
3. `data/<season>/` — `rosters-*.json`, `traded-picks.json`, `trades.json`, every season
4. Regenerate: `node dist/index.js --generate <season>` per season, then check `git diff -- output/`

Miss step 3 and nothing errors: the column simply falls back to alphabetical ordering because the `DRAFT_ORDERS` entry no longer matches any owner in the snapshot.

**A renamed team keeps its old name in the seasons it played under it.** The rename sweep above rewrites everything that *joins* on a name; `LEAGUE_HISTORY` is the one place that does not get rewritten, because a row there is a record of what happened and 2006 was won by the Winnemucca Muckers. `TEAM_ALIASES` in `league-info.ts` maps the old name to the current one, and the Trophy Case folds through it before counting, so the owner's record stays whole while the table above it stays accurate. A footnote under the Trophy Case names the old name, derived from the map and from what the history still says, so it takes itself off if the last row naming that team is ever changed.

- **`Riverstone Stoners` were the `Winnemucca Muckers`** through 2023, renamed for the 2024 season. Not a folded team: they are one of the ten in `ACTIVE_TEAMS`, and their two championships (2006, 2008) count on the Riverstone line. The old name stays in `TEAM_CITIES` (→ `Winnemucca`) because it still renders in the history rows it won.
- **`ACTIVE_TEAMS` in `league-info.ts` is the list of the ten teams currently playing**, and the only thing that decides which Trophy Case table a team lands in. A team that leaves is one deletion there; the retired table fills itself from whatever the history names that this list does not.

## Season Checklist

Operational cadence, verification steps, and automation notes live in `RUNBOOK.md`.

**Draft day** (typically late August):
0. Update `DEFAULT_LEAGUE_ID` in `src/index.ts` to the new season's league (see League section)
0a. **Once the offseason starts** (the next one is 2027): add the season to `DRAFT_ORDERS` in `tiers.ts` and to `DRAFT_DATES` in `league-info.ts`. Those two entries are also what **puts the home page's draft countdown card back**: it retires itself the moment a draft starts rather than sitting at 0 DAYS for eleven months, and it returns when a season has both. Nothing is commented out and there is no flag to flip, so a missing entry just leaves the home page in its in-season shape (prize pool card in the hero row, League at a Glance beside the photos), with no error
1. Before draft: `npm run dev -- --snapshot pre-draft`
2. After draft: `npm run dev -- --snapshot-draft <season>`
3. After draft: add the season's draft id to `SLEEPER_DRAFT_IDS` in `league-info.ts` (see the League section). Hand-added on purpose, and a missing entry just renders no `Draft Results` pill on the tiers hub, with no error
3a. After draft: add the season's `<season>:post-draft` entry to `TIER_CONFIGS` in `tiers.ts`. No entry means no tier bars, with no error. **Run step 2 before waivers open**: the capture reads the live roster (see Post-Draft Snapshots)

**After NFL Week 18** (~early January):
4. Final rosters: `npm run dev -- --snapshot end-of-season`
5. Update the hand-maintained season records in `league-info.ts`. **No command writes any of these**, so a season that nobody types up leaves the site a year stale with no error anywhere:
   - `LEAGUE_HISTORY`: the season's three bracket finishes and its Total Points team. **Total Points means the full season, playoff weeks included**, which is the basis every season from 2012 uses and the one the prize is actually awarded on. The obvious Sleeper field is the wrong one: `rosters[].settings.fpts` is the regular season alone, so ranking on it names the wrong team in any year a deep playoff run changes the order. Sweep `/league/{id}/matchups/{week}` for weeks 1-17 instead. 2006-2011 is regular-season-only because that is how that era recorded a season, and it is a closed era rather than a choice a new season gets to make
   - `SEASON_HONORS`: that year's honor cards, which the home page and History page both render
   - `STAT_ERAS`: any scoring record the season broke, added to the **current era's** block. Check the season against every row the era already carries, not just the obvious ones. A season that breaks nothing adds nothing, which is the normal case
   - `PRIZE_SEASONS`: final payouts, and flip the season to `final`
   - `SLEEPER_DRAFT_IDS` and `TIER_CONFIGS` belong to draft day (steps 3 and 0), not here
6. Freeze the season's rules, which is three steps in one commit and the only place order matters. Copy `output/rules.html` to `output/rules-<season>.html` and `git add` it, add that season to `RULES_PAGE_SEASONS` in `rules.ts`, then move `RULES_SEASON` forward and rewrite `RULES_SECTIONS` for the new year. Adding the season before committing the file publishes a link to nothing, and nothing errors

The three snapshot steps auto-fetch traded picks. Post-draft snapshots can be created retroactively; pre-draft cannot — the draft consumes the keeper selections, so they must be captured while `status` is still `pre_draft`. Re-run step 1 as keepers trickle in; the last run before the draft is the one that counts.

**Pre-draft overwrite guard**: re-capturing pre-draft is the expected workflow, so plain existence never blocks a write. Two things do, both bypassable with `--force`:
- **League past `pre_draft`** (`preDraftWindowClosed()` in `snapshot.ts`, checked in `snapshotAndGenerate()` before the 15MB player fetch). Sleeper has already consumed `roster.keepers`, so the capture could only be worse than the file it replaces. This is what stops a daily keeper-watch job left running past draft day from erasing the record.
- **Fewer keepers than the saved capture** (`saveSnapshot()`). Nothing legitimately un-picks a keeper, so this is a bad read, not an update. Equal or greater counts write normally.

Both throw `SnapshotGuardError`, which `index.ts` prints without a stack trace. The catch handler sets `process.exitCode` rather than calling `process.exit()`: on Windows, exiting outright while a just-completed `fetch` is still tearing down trips a libuv assertion and returns a crash status instead of 1.

## Traded Picks

One file per season: `data/<season>/traded-picks.json`, holding **every** pick the league reports across all draft seasons. Filtering happens at render time via `picksForDraft()` / `picksAwaitingDraft()` in `snapshot.ts`.

- **The `season` field means which draft the pick belongs to, never when it was traded.** A 2026 league's list is mostly trades made during 2025.
- **Trade dates come from a lineage-wide transaction sweep**, since `/traded_picks` carries no timestamp. Query a single league alone and every date silently vanishes — a fresh league returns the picks but zero transactions. Keying, collision rules, and the causes of a missing `tradedOn`: `docs/data-capture.md`.
- **Sealing**: a season's file stops being rewritten once a newer season has a data directory (`saveTradedPicks()` returns `undefined` when it skips). Re-fetching a sealed season would re-resolve owner names against current team names and quietly rewrite history.
- **Roster pages are the only place picks render.** The home page carried its own table until the Aug 2026 gallery pass; its hero card now reads "Current Tiers & Traded Picks" and links to the newest roster page instead. That is why `regenerateIndex()` loads no pick data at all, and why nothing on the home page needs a live fetch.

**Display rules** (columns Season, Round, Original Owner, Current Owner, Traded On; heading always "Traded Picks"; "None" when empty):

| Page | Shows |
|------|-------|
| Season N pre-draft | `season === N` — only the draft about to happen |
| Season N post-draft | `season > N` |
| Season N end-of-season | `season > N` |

## Roster & Player Ordering
- **HTML column order**: Draft slot order (post-draft round 1 pick order) via `loadDraftOrder()`. With no post-draft snapshot yet it falls back to `DRAFT_ORDERS[season]` in `tiers.ts`, which keeps a pre-draft page's columns lined up with the post-draft page that will sit beside it; alphabetical only if neither exists.
- **Post-draft tables**: tier blocks, **no round column**, and no row labels of any kind, the same shape the pre-draft and end-of-season pages already had, and the same shape the league's own 2022 and 2023 post-draft sheets use. A round still decides which block a player lands in and where he sits inside it, it is just not printed. **This is a tiers page, not a draft record**: Sleeper's own board is one click away on the Keeper Tiers hub and is the better account of what happened in the draft. Dropping the column also dropped the gaps that came with it, since a per-round row left a blank in nine columns whenever one team held an extra pick, and another hole wherever a team had traded or cut one. `buildPostDraftTierRows()` in `roster-grid.ts`; a post-draft page with no tier config falls through to `buildSequentialRows()` and simply lists each roster in order.
- **Keepers open their tier**, above that tier's drafted players. Which tier is `keeperTier` on the player, stamped at capture (see Post-Draft Snapshots) and never derived at render time, so a page regenerates from its own snapshot alone. A keeper with no `keeperTier` falls back to the top tier, which is where the roster slots keepers fill actually sit. They keep the yellow highlight and the legend under the table, which is now the only thing marking them. A throwback year has no keepers and nothing changes.
- **Live snapshots**: JSON alphabetical by owner; players sorted by position (QB, RB, WR, TE, K, DEF) then alphabetically.
- **Post-draft snapshots**: JSON by draft slot; players in draft pick order with `round` number.
- **End-of-season tiered**: Players grouped by original draft round (tier follows player, not owner). Sort by draft round within tier. Undrafted go in last tier. In last tier: DEF second-to-last, K last. Round lookup via `loadDraftRoundsFor()`.
- **Pre-draft tiered**: Same tiered layout, but keepers float to the top of their own tier — keeping a player never moves them to a different tier, and several keepers in one tier just stack there in round order. Below the keepers the normal sort resumes, so DEF/K still land last in the final tier.

## League Rules

**Throwback Years**: Every 5 years (2025, 2030, 2035, ...), no players are kept from the previous season — everyone drafts fresh. This affects:
- End-of-season tier labels are descriptive (e.g., "TIER 1 — Drafted Rounds 1–5") because players represent only what was drafted that year
- Pre-draft snapshot is skipped (no keepers = no interesting pre-draft state to record), so a throwback season shows only two stage pills on the Keeper Tiers page and carries a Throwback badge there saying why. **That badge comes from `isThrowbackSeason()` in `league-info.ts`, which computes the five-year cadence** — never from the absence of a pre-draft page, which is what the pre-redesign badge did and which reads a missed capture as a league rule
- The League History page marks it in three places, all from the same `isThrowbackSeason()`: the `THROWBACK_BADGE` chip on that season's honor-card heading, a clay fill on the whole row in the history table, and a `HIST_FOOTMARK` star on its season cell tying it to a `&#9733; Throwback year` legend under the table. All derived, so 2030 brings them back with no edit
- Non-throwback years (2026, 2027, ...) have keeper rules that shift the tier boundaries — see the keeper-year column of the rules page's tier table (T1 rounds 1–3, T2 4–8, T3 9+, set by the commissioner Aug 2026)

**Non-throwback tier rules** (2026 and beyond): a keeper-year draft runs 14 rounds behind the 3 keepers, and its tier boundaries are T1 = rounds 1–3, T2 = 4–8, T3 = 9+ (decided Aug 2026; the rules page's keeper table is the published statement). `2026:post-draft` was set on draft day (Aug 29, 2026) and `2026:pre-draft` earlier still (it tiers by the 2025 draft, so it needed no such rule); `2026:end-of-season` is added in January, with the same boundaries and descriptive labels.

**Sleeper slots keepers nowhere, and that question is settled.** The 2026 board ran a straight 17 rounds with no keeper marked on any pick, so keepers reach the page only because `takePostDraftSnapshot()` merges them in from the live rosters (see Post-Draft Snapshots). They carry **no round of that draft**, so nothing about the draft can place them. The rules do: a kept player **climbs one tier**, from the tier the previous season's draft put him in, and a free-agent pickup starts in the last tier. `loadKeeperTiers()` in `snapshot.ts` reads that origin off `<season>:pre-draft`'s config against the previous season's rounds, which is the same tiering that season's own pre-draft page renders, so the two pages cannot disagree about where a keeper started. Verified against all 30 of 2026's keepers: eight teams kept one from each 2025 tier and land 2 in T1 and 1 in T2, and the two that used the downward-substitution rule to keep two Tier 3s land 1 and 2. **End-of-season inherits this problem and has not solved it**: `loadDraftRoundsFor()` sends an end-of-season snapshot to the same season's post-draft file, where a keeper has no round, so `buildTieredRows()` would bucket all three into the undrafted tail. Decide that in January, not now.
Confirmed in the 2026 league (Aug 4, 2026): `settings.max_keepers` is `3` and `roster.keepers` is the authoritative selection (kept players also remain in the carryover `players` array, so `keepers` is the only way to tell them apart). Keeper selection was still in progress — 1 of 10 teams had picked.

## Tiers
Full-width colored separator rows dividing the table by draft value. Configured per `"season:snapshotType"` in `src/tiers.ts`.

- **Config**: `TIER_CONFIGS` map; each entry is `{ label, beforeRound }[]`
- **Colors**: T1 dark green `#1a6b2a`, T2 dark gold `#8b6914`, T3 dark red `#8b1a1a`
- **2025 boundaries** (throwback): T1 = rounds 1–5, T2 = 6–10, T3 = 11+ and undrafted. Post-draft and end-of-season labels are both descriptive (see League Rules above); post-draft drops the `/ Free Agency` tail its end-of-season twin carries, since nothing but the draft has reached a post-draft roster.
- **2026 post-draft** (first keeper year on Sleeper): T1 = rounds 1–3, T2 = 4–8, T3 = 9+, narrower than a throwback year's because the draft fills 14 slots rather than 17. Labels name the drafted rounds (`TIER 1 — Drafted Rounds 1–3`), matching every other config on the site. Keepers are placed by their climb rather than by these boundaries, so a team's T1 is its 2 climbed keepers plus rounds 1–3, and its T2 is 1 keeper plus rounds 4–8. **The label describes the drafted players and not the keepers above them**, which is the cost of naming rounds on a block that holds both; the keeper highlight and the legend carry the exception, exactly as they do on the pre-draft page, whose labels have always named rounds over a block of keepers.
- **2026 pre-draft**: same 1–5 / 6–10 / 11+ boundaries, but the rounds are **2025's**. `loadDraftRoundsFor()` sends pre-draft snapshots to the *previous* season's post-draft file, since nobody on a carryover roster has been drafted in the upcoming draft yet. Labels name the year ("Drafted Rounds 1–5 (2025)") so they don't read as 2026 rounds on a page headed 2026.
- **Adding a season**: Add entry to `TIER_CONFIGS`. No config = no tier rows.
- **Rendering**: all three snapshot types are tier blocks now, and none carries a row-label column. Post-draft: `buildPostDraftTierRows()`, which reads each player's own `round` off the snapshot. Pre-draft and end-of-season: `buildTieredRows()`, which reads a `DraftRoundLookup` keyed by name instead, since those rosters carry no round of their own. Both bucket by tier, sort within (keepers first), and let max-players decide the row count. The one behaviour that is not shared: `buildTieredRows()` pushes DEF and K to the foot of the last tier, and the post-draft builder does not, because a post-draft column is a draft-order listing.
- **`beforeRound` is not one thing.** `buildPostDraftTierRows()` and `buildTieredRows()` read it as a **draft round**; `buildSequentialRows()` reads it as a **1-based row index**. Sequential is the fallback when a tier config exists but `draftRounds` comes back empty, so the same config puts the bars in different places depending on which path runs, silently and with no error. Spelled out in the `TIER_CONFIGS` JSDoc.

## Draft Order
Upcoming season's draft order on index page. Configured in `DRAFT_ORDERS` in `src/tiers.ts` (key: season, value: owner names in pick order). `getLatestDraftOrder()` returns most recent. Add new entry each year; previous entries can remain.

## Page UI

Structure, section order, and layout reasoning for all three page parts (site header, index page, roster page) live in `docs/site-design.md`. Exact classes live in `html.ts`. What follows is only the set of rules that break something silently if violated.

**One layout at every width.** When something doesn't fit a phone, shrink what's in it (type, padding, name length); don't render a second structure. The League History table's stacked-block phone variant was built and reverted for exactly this reason.

- **Sticky header depends on `TABLE_WRAP`'s height cap, and the cap is one whole screen.** `TH` carries `sticky top-0 z-10`, which pins to the nearest scrolling ancestor. Drop the `max-h` and the header stops sticking with no error. The cap is `100dvh`, deliberately **not** `100dvh` minus the block above the table. That subtraction (15rem, briefly a `20rem`/`md:17rem`/`lg:15rem` ladder) reserved ~240px for page furniture that scrolls away the moment the page scrolls, then held the box to 582px of an 822px window forever after; the grids render 619–694px, so the reservation alone put a second scrollbar beside a table that would otherwise have fitted the screen. At `100dvh` the box is scrollable only when the grid cannot fit a screen, which is the same moment the sticky header is worth having. Changing the site header's height no longer moves this number, and neither does a breakpoint.
- **The nested scroll container is a CSS constraint, not a preference.** The grid is wider than any viewport, containing that sideways scroll needs `overflow-x`, and a box with one axis scrollable computes the other from `visible` to `auto`, which makes it the scrollport for every sticky descendant. So contained horizontal scroll and a viewport-pinned header cannot both be had, and "just let the window scroll both ways" would slide the site header, the footnotes and the Traded Picks table sideways with the grid. Don't re-litigate this without a new fact.
- **The page's own vertical scrollbar is not the table's, and it is correct.** A roster page carries ~640px below the table (keeper legend + column note, the Excel pill, the Traded Picks heading and its table, Back to top, the timestamp footer, `pb-10`), so the document exceeds the viewport no matter what the cap is set to; only removing content would remove it. The cap governs the *inner* scrollbar at the table's right edge, which under the current grids appears only on viewports shorter than ~710px.
- **Keeper highlight must stay after the position rules.** `.keeper { background: #ffff00 }` overrides the position tint by source order, since both are single-class selectors. Moving it up kills the highlight.
- **`PILL_EXPORT` swaps `inline-block` for `inline-flex`, never adds it.** Two `display` utilities on one element resolve by stylesheet order, not attribute order, so the loser is picked silently.
- **`SECTION_H2` is the only section heading style.** Both the index sections and `tradedPicksSection()` use it. A hand-written duplicate existed once and had to be kept in sync; don't reintroduce a second one. `ROW_LABEL` (the inline label on the closing link rows) is the same typography with different spacing, so both are built from `LABEL_TYPE` rather than repeating it. **`tradedPicksSection()` currently renders `mt-0 mt-8`** on its `<h2>`, since it appends `mt-8` to a constant that already carries `mt-0`; it resolves to 32px by Tailwind's sort order rather than by intent. Fixing it properly means a `SECTION_H2_BASE` split like `HIST_TH_BASE`, which is a docs edit too.
- **`CARD` is `CARD_BASE` plus a radius, and hero cards take `CARD_BASE` alone.** Two `border-radius` utilities on one element resolve by stylesheet order, not attribute order — the `PILL_EXPORT` trap again. Never write `${CARD} rounded-[14px]`.
- **Wrap floors go through `flexFloor(px)`, never a bare `min-w-[Npx]`.** It emits `min-w-[min(Npx,100%)]`. A plain `min-width` is a floor the box cannot shrink past even when it is alone on its row, so the home page's 460px gallery column would push a 430px phone into horizontal scroll. Capping at `100%` keeps the desktop wrap point and lets the column collapse.
- **The draft order card is sized to its longest team name, and the gallery absorbs the remainder.** A row is `px-5` + an 18px number + `gap-4` + the name, so the card needs `74px + text`; "South Town Freedom Fighters" measures 210px at 15px Schibsted Grotesk, hence the 320px `flexFloor` and the `flex-1` / `flex-[1.9]` split. The row has no `whitespace-nowrap`, so a longer name added to `DRAFT_ORDERS` wraps onto a second line silently. Re-check both numbers when one lands, and remember the two columns are zero-sum: narrowing the card widens the photos, which crop tighter rather than growing taller. **The card renders only until its season's draft runs**; after that `leagueFactsHtml()` takes the slot (see the seasonal-slots bullet below), in the same `flex-1` / 320px-floor shell so the gallery split is undisturbed.
- **The gallery's `max-h-[860px]` is what makes its photos crop at all.** They are `object-cover` in `min-h-0` flex children, so without a cap their intrinsic heights set the column. `object-position` (`GalleryPhoto.focus`) and `GalleryPhoto.weight` also do nothing without it. The cap is set by where the photos' subjects sit, not by the draft order card (~443px) beside it: pairing with the card is what the old 620 did, and it cut the tops of heads off in both photos. Derivation: `GALLERY_MAX_H` in [html.ts](src/html.ts).
- **The gallery lightbox is an enhancement over a working link, and must stay one.** Each photo is a plain `<a>` to its own full-size file; `LIGHTBOX_SCRIPT` intercepts the click into a native `<dialog>` and returns early when `showModal` is missing, so the fallback is the anchor itself. Swapping the `href` for a `#` or a `data-` attribute silently deletes the no-JS path. The dialog markup renders on the home page and the Photo Gallery, each gated on its own photo list (`lightboxHtml(photoCount)`), and closes on any click that is neither the image nor a `data-lb-nav` button, which is the entire close behavior, including the × button. **A new control inside the dialog must carry `data-lb-nav` or clicking it closes the overlay**, which is what the attribute exists for: the exemption is a property of the markup, so the close rule never has to learn a third element by name.
- **No inert spans remain in home page body copy.** "All 20XX prize winners" became a live link in Aug 2026 and "More in the Photo Gallery" followed when the gallery page landed; `PLANNED`, the body-copy twin of `NAV_PLANNED`, was deleted with its last caller. A future planned destination gets a new span and a reinstated constant, never a link to nowhere.
- **The gallery grid renders every photo uncropped, and the home column's crop must not migrate there.** `archiveFigureHtml()` in [html.ts](src/html.ts) is the home figure at the photo's own aspect (`w-full h-auto`, no `object-cover`, no height cap): the league's photos are edge-to-edge group shots and tight trophy shots, and a uniform cell has to clip the subject of one of them (a 4:3 cell was the first cut and took the tenth owner's face off the 2025 draft photo). The home column crops because it shares a height budget with the draft order card; the gallery page scrolls, so nothing forces a crop. That is also why `ArchivePhoto` carries no `focus` and no `weight`: with no crop and no shared height, there is nothing for either to steer.
- **The gallery's rows are justified flexbox, and proportionality is the whole mechanism.** `archiveFigureHtml()` in [html.ts](src/html.ts) gives each figure `flex-[<aspect>_1_<aspect*220>px]`: basis and grow both proportional to the photo's aspect keep every width in a row proportional to its aspect, which is the one distribution that renders a row of mixed aspects at a single shared height, uncropped. `GALLERY_ROW_H` (220) is the resting height; rows stretch to ~300px filling the measure. **The closing `flex-[999_1_0px]` spacer is load-bearing**: drop it and the last row's photos stretch to fill the full measure. `ArchivePhoto.width`/`height` must match the file on disk (read them with ffprobe at cut time): a wrong pair silently mis-heights its whole row and lies to the `<img>` size attributes.
- **The gallery is one flat run in `PHOTO_ARCHIVE`'s array order, newest subject first, and the two photo lists are deliberately separate.** Array order is the render order (the `PrizeSeason.prizes` rule) and the caption under each photo carries its year, so the page has no season headings, no anchors and no sub-nav. Ordering follows the season a photo is *about*, never its capture date (the year-prefix rule in `docs/photos.md`). The list is not reconciled with `GALLERY` (the SEASON_HONORS / LEAGUE_HISTORY call), so a home-featured photo is entered in both, with the cut for each slot.
- **`lightboxHtml(photoCount)` takes a count, not a flag**, because its two callers gate on different lists (the home page on `GALLERY`, the gallery on `PHOTO_ARCHIVE`) and because the count decides two things at once: zero drops the overlay, and one drops the prev/next arrows inside it while keeping the overlay. `LIGHTBOX_SCRIPT` is data-free (it queries `a[data-lightbox]` and returns early without the dialog) and ships on both pages unchanged. An empty archive drops the dialog and the rows for a "No photos yet." notice.
- **The lightbox steps through the photo links in DOM order, and that list is the only playlist.** `LIGHTBOX_SCRIPT` reads `a[data-lightbox]` off the page, so the arrows walk `PHOTO_ARCHIVE`'s order on the gallery and `GALLERY`'s on the home page with nothing to keep in sync, and `show()` reads a frame out of a link exactly as the click handler does, so opening and stepping cannot drift. **Stepping wraps** rather than disabling an arrow at each end, which also keeps both arrows in one state and spares them a disabled style. ArrowLeft / ArrowRight do the same on a `keydown` bound to the dialog; Escape is the native `<dialog>` behavior and is not bound here.
- **The lightbox never renders a photo above 1:1, and the cap is read off the image.** `fit()` in `LIGHTBOX_SCRIPT` sets `max-width`/`max-height` to the frame's own `naturalWidth`/`naturalHeight` on load, because the image is `flex-1` and `object-contain` otherwise scales it up to whatever the overlay has spare: the 318x496 champion shot rendered at 2.03x on a laptop, the two collages at 1.38x and 1.71x. Reading the natural size off the loaded image rather than off a recorded number means no second copy of a dimension that already lives on disk, covers `GALLERY` (which records none) as well as `PHOTO_ARCHIVE`, and cannot drift when a file is recut. **The `min(100%, …)` wrapper is load-bearing**: a bare pixel cap would override the `max-w-full` that keeps a 2000px cut inside a phone. The inline pair is cleared at the top of `show()`, so a frame never inherits the size of the one before it.

Take the start week from `export?TYPE=playoffBrackets`, **not** from `lastRegularSeasonWeek`, which reports 13 for every MFL season and is stale for 2021–2024. **Week 14 of 2021–2024 is a game against the league median, not a bye**: `export?TYPE=schedule` shows zero matchups there, but `leagueStandings` gives every franchise 14 decisions, and across all forty franchise-seasons the five teams above that week's median took a win and the five below took a loss, with no exceptions. The check that works is `curl -sL -A "Mozilla/5.0" <url>` piped through `grep -o -i -m1 '<title>[^<]*</title>'`, the same shape the `MFL_SEASONS` id check uses, with a second grep for the sign-in string: a real doc carries a `<title>` and runs ~215KB, the sign-in wall carries no title and runs ~9KB. Like the MFL sweeps, **the script that swept all seventeen is not in the repo**: nothing here reads these docs at runtime, and a one-time check does not justify a pipeline. 2011 was the one link that failed the first sweep, was published on 2026-08-22, and all seventeen have passed since.
- **`SUB_H3_BASE` exists so a caller can set its own margins**, the `HIST_TH_BASE` split for the same reason: the rules page's part-headings want space above them except for the first in a card, and appending `mt-6` to a `SUB_H3` that already carries `mt-0` is two `margin-top` utilities on one element, resolved by stylesheet order rather than intent. `SUB_H3` is the base plus `mt-0 mb-3` and renders byte-identically to what it was, so its two existing callers were untouched. A `first:mt-0` on top of a caller's own `mt-*` is safe, since variants sort after their unprefixed forms.
- **Root-level pages are flat files, not directories.** `output/history.html` rather than `history/index.html`: Cloudflare Pages serves it at `/history` either way, but a flat file also opens over `file://` during local preview, which is how this project is previewed. Nav links keep the `.html`.
- **`noindex` without a `robots.txt` `Disallow`.** Disallowing blocks the fetch, so the crawler never reads the `noindex`. Staying crawlable is what makes the directive work.
- **Head metadata is written for an unfurl card, never a search result.** `noindex` means no `<title>` or `description` on this site ever reaches a SERP; the only thing that renders them is the preview a chat client draws from a pasted link. So descriptions are cut to **~100 characters**, where iMessage and Discord clip, not the 155 a snippet allows, and the useful half goes first.
- **`SITE.wordmark` is the only thing that names the site**, supplying every `<title>` and every `og:site_name`, so the tab and the header cannot disagree the way they did until Aug 2026. Titles read `<wordmark> — <page>` (em dash; the home page takes the bare wordmark). The registered Sleeper name `Fantasy For Life (FFL)` now appears in exactly one place, the line under a roster page's h1, read off `snapshot.leagueName`. The `LEAGUE_NAME` constant in `index.ts` and the `leagueName` parameter on all four root-page generators were deleted with it. **Do not reintroduce either**: a second copy of the name is what let the two spellings drift.
- **`og:url` and `og:image` are the site's only absolute URLs, and both are gated on `SITE.origin`.** Everything else is relative so `file://` preview keeps working, but an unfurler has nothing to resolve a relative reference against. Each generator passes its own `path`; `origin` is `""`-checked so an unset host drops both tags instead of emitting a broken URL. **`twitter:card` must stay `summary`** while the image is `ffl-avatar-512.png`, which is square. `summary_large_image` wants a 1.91:1 banner that does not exist yet, so changing the card type means cutting a new asset first. Both directions of the gate need exercising after any edit (see the render-state note under Verifying Changes).
- **The roster table itself was left alone by the Aug 2026 redesign.** Position tints, tier bars, keeper yellow, and cell borders are duplicated into `xlsx.ts` — changing one means changing both.
- **Column-order note** comes from `columnOrderNote()` in [roster-grid.ts](src/roster-grid.ts), which both renderers call. It requires `columnsInDraftOrder` and is excluded outright on end-of-season pages; the reasoning for that exclusion is in `docs/site-design.md` and has already been argued once.

## Excel Export

`output/<season>/rosters-<type>-<season>-ffl.xlsx`, generated by `generateWorkbook()` in `src/xlsx.ts` and written by the same call that writes the page. Two sheets: the grid, and that page's traded picks. Write-only — nothing reads it back, and the page's download link is the only consumer.

Hand-rolled OOXML with no dependency: `src/zip.ts` writes the zip container, `src/xlsx.ts` writes the XML parts. Both are deliberately narrow — no reading, no zip64, no shared-string table (cells use `t="inlineStr"`).

Sheet layout, naming reasoning, and the CSV export it replaced: `docs/excel-export.md`.

**Edit traps:**
- **`STYLE` ids in `xlsx.ts` are bare indexes into the `cellXfs` list in `STYLES_XML`.** Inserting an entry mid-list silently repaints every cell after it. Edit the two together.
- **Fill 0 (`none`) and fill 1 (`gray125`) are reserved by the format.** Excel misreads the whole style table if anything else takes those slots.
- **Colors are duplicated from `ROSTER_STYLES` in `html.ts`** — position tints, keeper yellow, the three tier colors. Surviving the export is the entire point, so change both lists together.
- **Zip timestamps are fixed at 1980-01-01** (`src/zip.ts`) so regeneration over unchanged data produces identical bytes. A real clock would make every run a diff and break the `git diff -- output/` check.
- **`.gitattributes` marks `*.xlsx binary`** so no CRLF filter can ever touch a deflate stream. The `binary` macro unsets `text`, which is what keeps the repo-wide `* text=auto eol=lf` above it away from a workbook. Keep the binary rules **after** that line: the last matching pattern wins per attribute, so reordering them silently hands every `.xlsx` back to the EOL filter.
- **Both renderers consume `buildRosterGrid()`.** Column order, tier placement, keeper-first sorting, and round labels are decided once. Never render a workbook straight off the JSON.
- **Renaming either output orphans the committed file under the old name** — the generator writes the new name and leaves the old beside it, still tracked and still served. `git rm` the strays in the same commit. Names come from `pageFileName()` and `exportFileName()` in `snapshot.ts`.

**Before committing a styles or sheet change, open the workbook in Excel.** Static XML checks don't prove it opens. Procedure and its traps: `docs/excel-export.md`.

  (daily in Aug, Thursdays Sep–Jan), commits `data/` and `output/`, and pushes to `main`, which

## Verifying Changes
- No test framework. Exercise logic with `node --input-type=module -e '...'` importing from `./dist/` after `npm run build`.
- No linter or formatter is configured for `src/`; `npm run build` (tsc) is the only gate — and `tsconfig.json` sets `strict` but **not** `noUnusedLocals`, so a dead import or unused const compiles clean. After removing the last call to something, `grep -n '<name>' src/` rather than trusting the build.
- **Size a layout before picking a breakpoint** — nothing here renders CSS. Import the data from `./dist/` and multiply character counts by the font metric (15px Schibsted Grotesk ~ 8px/char; 11px uppercase at `0.12em` tracking ~ 7.4px/char), then compare against viewport minus the page's `px-5` / `sm:px-8` gutters. That is how the League History table's three width tiers were set, and it ruled out shrinking type alone.
- **Size a table's *height* the same way, and count its rows off the generated HTML.** The roster grid renders 25px per data row and per header row and 23px per tier bar (`text-xs` is 12px/16px; `py-1` on `CELL`, `padding: 3px` on `.tier td`), so `rows*25 + tiers*23 + 25` is the table height: 619–694px across the three current pages. Count with `grep -c '^    <tr>$'` (that total **includes** the header row) and `grep -c 'class="tier '`. A loose `grep -c '<tr'` counts *lines* containing the tag, not rows, and overcounts by half.
- **Audit every scroll container at once**: `grep -ro 'class="[^"]*overflow-[^"]*"' output/ --include=*.html | sed 's/.*class=//' | sort -u`. Only a *capped* one (`max-h` plus `overflow`) can add an inner scrollbar; `TBL_SCROLL`'s uncapped `overflow-x-auto` never can, and `overflow-hidden` on a card is corner clipping.
- A scratchpad `.mjs` importing from `dist/` needs a **`file:///C:/...` URL**: a relative path resolves against the script's own directory, and a bare `c:\...` path is rejected as an unsupported URL scheme. `node --input-type=module -e` has neither problem.
- **Backticks die inside an inline `python -c "..."`.** Bash command-substitutes them within double quotes, so a replacement string carrying `` `HIST_TD` ``-style markup lands with those words deleted and the script reports success. Write the script to the scratchpad **with the Write tool**, then `python <path>`. A quoted heredoc is fine for a short prose-only edit but **not** for a script whose replacement strings carry template literals: a `<<'PY'` body of that shape dies with ``unexpected EOF while looking for matching `'` `` reported at the *last* line, which reads as a missing terminator rather than as the content problem it is. Same failure and same fix as the TypeScript line below. Either way this beats a `head`/`cat`/`sed` splice for multi-point edits to a file of template literals.
- **Don't heredoc a large block through Bash** — this is about size and embedded quoting, not language. A `<<'EOF'` block carrying `html.ts`-style template literals dies with ``unexpected EOF while looking for matching `'` ``, and a multi-edit *Python* script embedding `.md` and `.ts` prose dies the same way despite a quoted `<<'PYEOF'` delimiter. Past a few short replacements, write the script to the scratchpad with the Write tool and run it by path; that path has neither failure. For a multi-function rewrite, write the block to the scratchpad with the Write tool, then splice with `head -n N` + `cat` + `sed -n 'M,$p'` and rebuild. Single edits go through Edit. **Re-read both seams after a splice**: an off-by-one boundary leaves a stray line rather than an error, and in a `.md` file nothing will ever flag it.
- **Multi-line prose edits (`.md`, doc blocks) go through a Python heredoc**, never `sed`: `python - <<'PY'` doing `s.replace(old, new)` guarded by `assert old in s`, written back with `io.open(p, 'w', encoding='utf-8', newline='\n')`. The assert is the point: a silent no-match is what `sed` gives you for free. `newline='\n'` stops Python emitting CRLF and turning a two-line change into a whole-file diff. **Hold every edit in memory and write the files only after the last assert passes**, so a failed guard leaves the tree untouched rather than half-edited: the difference between rerunning a script and unpicking a partial one. (`python` is 3.11, `python3` is 3.14: separate installs.)
- **Assert the match *count*, not just membership**, when a replacement targets page shell markup. The home and Prize Tracker pages open with a byte-identical `<main class="max-w-[1080px] ...">`, and several card/section wrappers repeat across generators, so `assert old in s` passes while `s.replace()` edits two pages. Use `assert s.count(old) == N`.
- **Backslash escapes are eaten on the way into a Python heredoc.** `\n` in a `python - <<'PY'` block reaches the file as a real newline despite the quoted delimiter, so replacement text carrying `.join("\n")` lands corrupted while `assert old in s` still passes — the assert guards the *old* string. **Always use a raw string (`r'...'`)**; doubling is not reliable. `\\n` survives `python - <<'PY'` (piped to stdin) but is eaten down to a real newline by `cat > script.py <<'PYEOF'`, so the same replacement text works one way and corrupts the other. `r'...'` and `chr(92)` write correctly through both. A `.ts` file surfaces this as a tsc syntax error; a `.md` file surfaces it as nothing.
- **Anchor an insertion on the doc comment, not the declaration.** Replacing `export const X` to add a const above it drops the new one *between* `X` and its JSDoc, silently reassigning the comment to the wrong symbol. Both compile; only reading the seam catches it.
- **Renaming or dropping an `html.ts` constant is a docs edit too.** This file and `docs/` name them directly (`PILL_EXPORT`, `HISTORY_SECTIONS`, `TAB_ROW`), and **CSS class names inside an `extraStyles` block count too** (`.tbl-scroll`) — renaming one is four or five prose edits across two files. `grep -rn '<OLD_NAME>' src/ docs/ CLAUDE.md` before committing. A stale name reads as current and nothing will ever flag it, the same trap as a renamed output file left behind in `output/`. **User-visible copy is quoted in that prose the same way**, so grep the *string* too when a label changes or its element is deleted: a rule explaining why a strip reads "After the owner survey" outlives the strip silently. Deliberate history ("it said X first") is the one legitimate hit, so read each one rather than replacing blind.
- **A self-retiring element needs both directions exercised.** Several render only while the thing they explain is still true: the history table's "still being compiled" note, the Trophy Case's two footnotes and its rename superscript, `scoredColumns()` dropping a column no row scored in. Mutate the imported data so the condition goes false, re-render, assert it is gone, then restore and assert it is back. Checking only that it appears proves half of it, and the half that rots silently is the other half. **Assert absence on a string nothing else on the page can produce**: `<sup` is the Trophy Case's rename footnote as well as the history table's throwback star, so the obvious negative assertion fails on an element that was never in scope. Match the entity (`&#9733;`) or the whole cell, not the tag.
- **A non-empty `output/` diff still isn't proof of a visual change**, and two causes are common enough to check before hunting a regression. **Editing a comment inside `THEME` rewrites every page**, since the block is inlined into every head: a one-word change there is a one-line diff on all six. And **refactoring a constant into a base plus a variant reorders the class attribute**, so splitting `HIST_TD_SEASON` into `HIST_TD_SEASON_BASE` + `bg-white` moved that one utility to the end of the string and showed all 20 history rows as changed. Class attribute order never decides anything (stylesheet order does, which is the `PILL_EXPORT` trap), so that diff is noise. Read what moved, not how many lines did.
- **An optional block's spacing usually lives on its neighbour, so it has to toggle too.** `ruleChangesHtml()` gates both the `<p>` and the following grid's `mt-6` on the same `rules.intro`. Leaving the margin behind opens the card on a gap where the paragraph was, which renders as slightly-off padding rather than as anything obviously wrong.
- **A page-UI change is three edits and a regenerate**: the treatment in `html.ts`, its rule in the Page UI list above, its reasoning in `docs/site-design.md`, then `node dist/index.js --generate <season>` and read the `output/` diff.
- **A whole new root page is five edits, not three**: the generator in `html.ts`, its `get<Name>OutputPath()` in `snapshot.ts`, a `regenerate<Name>()` in `index.ts` **plus its call in `main()`** beside the other root pages, its `SITE_NAV` entry in `league-info.ts`, then the rules and reasoning in this file and `docs/site-design.md`. Forgetting the `main()` call is the silent one — the generator compiles and is simply never invoked.
- `output/` is committed, so regenerate then `git diff -- output/`: an empty diff proves no visual regression, a non-empty one shows exactly what changed. Only `--generate` is deterministic this way; anything that re-fetches rewrites `capturedAt`/`fetchedAt`, so its diff is never empty. **`git status` is trustworthy again as of Aug 2026, and `.gitattributes` is what makes it so.** `core.autocrlf` is `true` at system and global scope, so checkout wants CRLF while the generator, tsc and the Actions runners all write LF. Until the repo declared text attributes, every file the generator rewrote was stuck reporting `M` with an empty `git diff`, permanently: `git update-index --refresh` answered `needs update` and could not clear it, and it was never only an `output/` effect, since a `src/` or `.md` file did the same. `* text=auto eol=lf` pins checkout to LF so the two agree. Every blob was already LF, so the fix changed no committed content and `git add --renormalize .` stages nothing. **Deleting that line brings the phantom back**, one file at a time as the generator touches them.
- **Another session may be editing this same working tree.** `WORKTREES.md` describes isolating parallel sessions; without one they share `c:\Dev\fantasyforlife` and its index. The session-start `git status` is a snapshot that goes stale, HEAD can move mid-task, and a `git diff` run twice can mean two different things. **Re-check `git log --oneline -3` and `git status --short` before any commit or diff-based conclusion**, and if the tree holds changes you did not make, say so rather than bundling them. A session committing with `git add -A` or a file list overlapping yours will sweep your uncommitted work into its message, which no amount of re-reading the diff afterwards recovers.
- **To exercise a render state the committed data can't reach**, import the config object from `./dist/` and mutate it before calling the generator: `PRIZE_SEASONS["2026"] = {...}` then `generatePrizesHtml(...)`, writing the result to the scratchpad. Works for anything exported from `league-info.ts` or `tiers.ts`. This is how the prize page's live band, leading tag, split payout and all-time table were verified before shipping, since the real 2026 season has none of them yet.
- **Reading a published Google Sheet**: `pubhtml` renders its tables in JS now, so `WebFetch` and a plain `curl` both come back with only the title. Use the CSV endpoint instead: `curl -sL "<pub-base>/pub?gid=<gid>&single=true&output=csv"`. Find the gids by fetching the `pubhtml` once and grepping it for `gid=[0-9]+`; omitting `gid` gives the first tab. `ARCHIVE_LINKS.prizeSheet`'s tabs are `gid=0` (2023), `461470939` (2024), `1933704036` (2025), and it names teams by city word, so a value lifted from it has to be expanded before it lands in `league-info.ts`.
- **Check your own added prose for em dashes with `git diff -- CLAUDE.md docs/ | grep "^+" | grep "—"`.** The existing docs use them heavily and ` — ` as a label separator is fine, so a whole-file grep is useless; only the added lines are yours to fix.
- To eyeball a generated file (page in a browser, workbook in Excel), use PowerShell `Start-Process <absolute path>`.
- `gh` is installed and authenticated: `gh run watch <id> --exit-status` follows a workflow run, `gh run view <id> --log` reads one, `gh api repos/<owner>/<repo>/releases/latest --jq .tag_name` gets an action's current major.
- No YAML parser is installed (Python has no `yaml` module either). Validate workflow edits with `npx --yes js-yaml <file>`, which leaves `package.json` untouched.
- `ffmpeg`/`ffprobe` are installed (winget `Gyan.FFmpeg`) and are the only image tooling: resize with `-vf "scale=W:H:flags=lanczos"`, encode with `-c:v mjpeg -q:v 2` (photos) or `-c:v png -compression_level 100` (marks). Read dimensions with `ffprobe -v error -select_streams v:0 -show_entries stream=width,height -of csv=p=0`. The Read tool renders both PNG and JPEG directly now that nothing is WebP, so a cut can be eyeballed without converting first; judge a downscale or compression artifacts by cropping a region and magnifying it with `flags=neighbor`.
- Before assuming API drift, diff live response keys against `src/types.ts` rather than trusting the docs (their `/players/nfl` size is 3x stale).
